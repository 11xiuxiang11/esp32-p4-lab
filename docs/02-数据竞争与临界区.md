# 02 · 数据竞争与临界区

## 一句话总结

**`g_counter++` 是"读-改-写"三步，三步之间被插队就会丢更新；临界区就是把这三步装进一道"一次只许一个人进"的门。**

---

## 概念

### 丢更新的完整过程

`g_counter++` 在 RISC-V 上是三条指令：

```asm
lw   a4, g_counter    ; ① 读
addi a4, a4, 1        ; ② 改
sw   a4, g_counter    ; ③ 写
```

假设 `g_counter = 100`，两个核同时执行：

| 时刻 | Core0 | Core1 | 内存 |
|---|---|---|---|
| T1 | `lw` → 100 | | 100 |
| T2 | | `lw` → 100 | 100 |
| T3 | 100+1 = 101 | | 100 |
| T4 | | 100+1 = 101 | 100 |
| T5 | `sw` → 101 | | 101 |
| T6 | | `sw` → 101 | 101 |

**加了两次，只加了 1。** 后写的覆盖了先写的。

插队来源：
- **单核**：tick 中断把任务切走（每 10ms 一次机会）
- **双核**：另一个核真的同时在跑（P4 两个 RISC-V 核，不需要"正好"）

### 竞态窗口

**从"读"到"写"之间隔的指令越多，窗口越宽，撞上的概率越大。**

| 窗口 | 表现 |
|---|---|
| 2~3 个周期（`g_counter++`） | 可能一次都不丢——**最危险**，因为测试全绿 |
| 几十个周期（读 → 空转 → 写） | 几乎必然丢，甚至丢到腰斩 |

### 临界区

**一段"同一时刻只允许一个执行流进入"的代码。**

P4 上由两件事实现：

| 动作 | 防谁 |
|---|---|
| 关**本核**中断 | 防本核 tick 把自己切走 |
| 抢**共享的自旋锁**（`portMUX_TYPE`） | 防另一个核同时进来 |

**关键点：关中断只关本核。** 另一个核照常跑，所以锁必须是共享的那一个。

### `volatile` 为什么不够

- `volatile` 保证：每次真去内存读，不被编译器缓存到寄存器
- `volatile` **不保证**：读-改-写是原子的
- 加了 `volatile`，三条指令一条不少，照样能被插队

> `volatile` 是给编译器看的，不是给调度器看的。

### 四种保护手段（选型）

| 手段 | 适用 | 代价 | 约束 |
|---|---|---|---|
| **临界区 / 自旋锁** | 极短（几十条指令）、不调 FreeRTOS API | 关本核中断 + 另一核自旋 | 里禁止阻塞调用 |
| **互斥量** | 逻辑较长、可能阻塞、需要优先级继承 | 上下文切换开销 | ISR 里禁用（B2-2 详讲） |
| **原子操作** | 单个变量加减/置位 | 一条 `amoadd.w` 指令 | 只保护一个变量 |
| **队列** | 传数据所有权、解耦 | 一次拷贝 | 下一章 |

## 代码

### 临界区模板

```c
#include "freertos/FreeRTOS.h"

/* ① 锁本体：全局静态，未加锁状态初始化 */
static portMUX_TYPE s_counter_mux = portMUX_INITIALIZER_UNLOCKED;

static void task(void *arg)
{
    ...
    /* ② 三步操作整体包起来 */
    portENTER_CRITICAL(&s_counter_mux);
    g_counter++;
    portEXIT_CRITICAL(&s_counter_mux);
    ...
}
```

### 四个版本，按上下文选

| API | 用在哪 |
|---|---|
| `portENTER_CRITICAL(&mux)` / `portEXIT_CRITICAL(&mux)` | 任务里（最常用） |
| `portENTER_CRITICAL_ISR(&mux)` / `portEXIT_CRITICAL_ISR(&mux)` | 中断里 |
| `portENTER_CRITICAL_SAFE(&mux)` / `portEXIT_CRITICAL_SAFE(&mux)` | 不确定上下文时 |
| `taskENTER_CRITICAL(&mux)` | 任务里（FreeRTOS 原生名，IDF 中等价） |

### 原子操作（单变量更便宜）

```c
__atomic_fetch_add(&g_counter, 1, __ATOMIC_SEQ_CST);
```

### 宽窗口实验写法（用来暴露问题）

```c
uint32_t tmp = g_counter;                 /* 读 */
for (volatile uint32_t k = 0; k < 32; k++) { }  /* 制造窗口 */
g_counter = tmp + 1;                      /* 写 */
```

修的时候**读、空转、写三步都要在锁内**，只锁最后一行无效。

---

## 实测数据（`p4-lab/main/race_demo.c`）

两个任务绑 Core0 / Core1，各做 10 万次：

| 版本 | 期望 | 实际 | 丢失 |
|---|---|---|---|
| 紧循环 `g_counter++` | 200000 | 200000 | **0** |
| 宽窗口（空转 32 圈） | 200000 | 100003 | **99997（≈50%）** |

宽窗口丢一半的原因：每次两个核都读到同一个值，各 +1 后写回同一个数 → 只算一次加。

---

## 易错处

| # | 错误 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 用 `volatile` 当同步 | 照样丢 | `volatile` 只防优化，不防并发 |
| 2 | `portMUX_TYPE` 定义在函数里 / 每个任务各定义一份 | 等于没锁 | 全局静态，所有相关任务共用同一个 |
| 3 | 只锁"写"，没锁"读" | 无效 | 读-改-写整体在锁内 |
| 4 | 临界区里放 `ESP_LOGI` / `printf` / `vTaskDelay` | 关中断期间阻塞 → 整核卡死、看门狗 | 日志放锁外 |
| 5 | `portEXIT_CRITICAL` 漏写（或有 `return` 分支没退出） | 锁永远不放 → 下次进入卡死 | 成对出现，所有出口都要 EXIT |
| 6 | 临界区太长 | 关中断久了丢 tick，时间精度下降，别的核空转 | 控制在几十条指令内；长了改用互斥量 |
| 7 | 任务函数 `return` | 断言 → 板子重启 | `vTaskDelete(NULL)` |
| 8 | 以为建了两个任务就在并行 | 高优先级任务抢占创建者，第二个任务没建出来 → 串行，测不出竞态 | 创建期间临时提高创建者优先级，或用信号量让任务同时起跑 |
| 9 | "测了 10 万次没丢，所以没问题" | 换编译器/换板子/加行日志就暴露 | 竞态的正确性是**设计保证**的，不是测出来的 |

# 02-B · 互斥量与优先级翻转（B2-2）

## 一句话总结

**临界区管"短且不能阻塞"，互斥量管"长且可能阻塞"；互斥量默认带优先级继承，所以"翻转"要用二值信号量才看得见。**

## 概念

### 临界区的三个局限

| 局限 | 后果 |
|---|---|
| 关中断期间 tick 停了 | 时间不准、实时性变差 |
| 另一核自旋等锁 | 白烧 CPU |
| 里不能调用会阻塞的 API | 但串口/Flash/I2C 这类最需要保护的操作恰恰耗时 |

### 互斥量 vs 自旋锁

| | 自旋锁（临界区） | 互斥量 |
|---|---|---|
| 拿不到时 | 原地转圈 | **去睡觉**，让出 CPU |
| 谁能用 | 任务 + 中断 | **只能任务** |
| 有主人概念 | 无 | 有（谁 take 谁 give） |
| 优先级继承 | 无 | **有**（`configUSE_MUTEXES=1`，IDF 默认开） |
| 适合 | 几十条指令 | 几百微秒到几毫秒、可能阻塞 |

### 优先级翻转

H（高）等锁，锁在 L（低）手里；M（中）不碰锁但优先级高于 L → M 抢占 L → L 放不了锁 → **H 被 M 间接拖住**。

真实案例：1997 火星探路者号反复重启，就是这个问题，远程打开优先级继承修好。

### 继承：触发 vs 有用（最容易搞混）

| 问题 | 答案 |
|---|---|
| 什么时候**触发** | 只要有**更高优先级任务在等这把锁**，holder 就被提升到等待者优先级 |
| 什么时候**有效果** | 只有**有中优先级任务想插队**时，结果才被改变 |
| 放锁后 | 恢复原始优先级（`xTaskPriorityDisinherit`） |

**推论：用互斥量时，只要有人在等锁，L 的优先级就一定被提升，与有没有第三方无关。** 想验证"继承存在"，必须直接打印持锁者的优先级，不能只看等待时间。

## 代码

```c
#include "freertos/semphr.h"

SemaphoreHandle_t mux = xSemaphoreCreateMutex();     /* 带继承 */
/* SemaphoreHandle_t sem = xSemaphoreCreateBinary();  二值信号量：无继承，且创建后是空的，
 *                                                    要先 xSemaphoreGive() 一次才能当锁用 */

xSemaphoreTake(mux, portMAX_DELAY);   /* 拿不到就无限等；也可给 100ms 选择放弃 */
/* ... 保护的操作 ... */
xSemaphoreGive(mux);

vSemaphoreDelete(mux);                /* 不用了再删 */
```

取证用的观测点：

```c
/* 在这把锁被更高优先级任务等待期间，holder 的优先级已经被提升 */
ESP_LOGI(TAG, "持锁中，我的优先级 = %d", (int)uxTaskPriorityGet(NULL));
```

## 实测（`priority_inversion.c`，L=2 / M=4 / H=6，同绑 Core0）

| 组 | 锁 | 有 M | H 等待 | L 放锁前优先级 | 解读 |
|---|---|---|---|---|---|
| ① | 互斥量 | 是 | ~270ms | **6** | 继承挡住 M，翻转被消除 |
| ② | 二值信号量 | 是 | **~470ms** | 2 | 无继承，翻转现形 |
| ③ | 互斥量 | 否 | ~270ms | **6** | 继承照样触发，但没人抢，看不出差别 |
| ④ | 二值信号量 | 否 | ~270ms | 2 | 对照组 |

## 易错处

| # | 错误 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 用二值信号量保护资源 | 无优先级继承，埋下翻转 | 保护资源用 `xSemaphoreCreateMutex()` |
| 2 | 以为"没有中优先级任务就不触发继承" | 判断错误 | 触发看等待者，效果看第三方 |
| 3 | 中断里 `xSemaphoreTake` | 中断不能阻塞 → 断言 | ISR 里用 `...FromISR` 版本或队列 |
| 4 | 忘了 `xSemaphoreGive` | 别人永远拿不到 | take/give 成对 |
| 5 | 两个锁交叉获取 | 死锁 | 固定加锁顺序，或只用一个锁 |
| 6 | 用二值信号量创建后直接 take | 永远拿不到（初始为空） | 先 `give` 一次 |
