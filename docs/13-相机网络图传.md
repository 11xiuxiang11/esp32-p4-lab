# 09 · 相机网络图传（MJPEG over HTTP）

> 对应实验：`EXP_MJPEG = 18`（`main/mjpeg_server.c`）
> 实测日期：2026-11-23

## 1. 链路长什么样

```
SC2336 ──MIPI-CSI──> ISP ──> /dev/video0 (RGB565 1024x600, mmap 缓冲)
                                  │  DQBUF：缓冲交给我们
                                  ▼
                        jpeg_encoder_process()   ← 硬件 JPEG 编码器（DMA2D 从 PSRAM 读）
                                  │  7~8 ms，输出 20~50 KB
                                  ▼
                        槽位（3 个 PSRAM 缓冲）+ 队列
                                  │
                                  ▼
                  httpd 任务：/jpg 发一张；/stream 循环发（multipart）
                                  │
                                  ▼
                    lwIP → esp-hosted → SDIO → C6 → Wi-Fi → 手机浏览器
```

任务划分：

| 任务 | 干什么 | 为什么这么分 |
|---|---|---|
| `cam_cap`（core 1，prio 6） | 独占 `/dev/video0`：DQBUF → 有人要图才编码 → QBUF | 相机 fd 只有一个所有者，避免两个任务抢缓冲 |
| `httpd`（IDF 内部） | 取编好的帧、发往 socket | 发送慢的时候只阻塞自己，不会把相机流卡死 |
| `mjpeg_boot`（core 0） | 初始化 + 等 IP | 启动流程可以和别的实验共用 |

**为什么编码不放在 HTTP 回调里**：回调里发一张图要 100~400 ms（受 Wi-Fi 带宽限制）。如果回调自己去 `DQBUF`，慢客户端会让相机没有空闲缓冲可写，整条流停摆。现在编码在相机任务里，httpd 只"取一张发一张"，客户端慢 → 丢帧，不积压。

## 2. 三个关键机制

### 2.1 V4L2 缓冲的"所有权"

`VIDIOC_DQBUF` 之后，这个缓冲**暂时归应用**，驱动不会往里写；`VIDIOC_QBUF` 才还给驱动。所以：

- 编码必须在 `QBUF` 之前做（本实验就是：DQBUF → 编码 → QBUF）；
- 想长期持有一帧（比如显示用），就别急着 QBUF，但那样会少一个可写缓冲。

### 2.2 硬件 JPEG 编码器

- 输入支持 RGB565 / RGB888 / GRAY / YUV422（P4 rev3.1+ 还有 YUV444 / YUV420）；
- 输出缓冲**必须**用 `jpeg_alloc_encoder_mem()` 分配：它按 cache line 对齐，`jpeg_encoder_process()` 里有断言，随便 `malloc` 会返回 `ESP_ERR_INVALID_ARG`；
- 编码器跟 LCD 的 DMA2D 共用同一个 DMA2D 池，面板和编码器同时跑时由 DMA2D 驱动排队。

### 2.3 零拷贝 + 背压

三个槽位，两个队列：

```
s_free_slots : [0][1][2]          空闲槽位号（uint8_t）
s_ready_jpegs: [msg][msg]         编好的帧（槽位号 + 长度 + 编码耗时）
```

- 相机任务：`xQueueReceive(free, 0)` 拿空槽 → 编码进这个槽 → `xQueueSend(ready, 0)` 投递；
- httpd：`xQueueReceive(ready, timeout)` 取帧 → `httpd_resp_send` → 把槽位还回 free；
- **拿不到空槽就丢这一帧**：消费端跟不上时宁可丢，也不排队等（等就变成延迟累积 + 内存堆积）。

需求用计数信号量 `s_demand` 表达：httpd 每要一张 `Give` 一次，相机任务每编一张 `Take` 一次。没人看图时相机任务几乎不占 CPU（只跑 DQBUF/QBUF）。

## 3. API 五项表

### `jpeg_new_encoder_engine()`

| 项 | 内容 |
|---|---|
| 用途 | 创建硬件 JPEG 编码器实例（P4 只有一个编码器，全局一个实例） |
| 参数 | `jpeg_encode_engine_cfg_t*`：`intr_priority`（0 = 驱动自选 1/2/3）、`timeout_ms`（单帧编码上限，比 30fps 的 33ms 大，本实验给 200） |
| 返回 | `ESP_OK` / `ESP_ERR_NO_MEM` / `ESP_ERR_INVALID_ARG` |
| 失败条件 | 已经建过一个实例、内部 DMA2D 申请不到、内存不足 |
| 易错点 | 不调 `jpeg_del_encoder_engine()` 就反复 `new`，第二次必失败 |

### `jpeg_alloc_encoder_mem()`

| 项 | 内容 |
|---|---|
| 用途 | 给编码器分配输入/输出缓冲（cache line 对齐 + 指定内存方向） |
| 参数 | `size`、`jpeg_encode_memory_alloc_cfg_t`（`buffer_direction` = 输出缓冲 `JPEG_ENC_ALLOC_OUTPUT_BUFFER`）、`allocated_size` 出参 |
| 返回 | 缓冲指针；失败返回 `NULL` |
| 失败条件 | PSRAM 不够（本实验 3 × 256 KB） |
| 易错点 | 输出缓冲地址不对齐 → `jpeg_encoder_process` 直接 `ESP_ERR_INVALID_ARG`；**实际对齐后的大小 ≥ 你请求的大小**，按出参算容量 |

### `jpeg_encoder_process()`

| 项 | 内容 |
|---|---|
| 用途 | 把一帧原始像素编成 JPEG 码流（含 JFIF 头） |
| 参数 | 编码器句柄、`jpeg_encode_cfg_t`（`width`/`height`/`src_type`/`sub_sample`/`image_quality`）、输入缓冲、输入字节数、输出缓冲、输出容量、`out_size` 出参 |
| 返回 | `ESP_OK` / `ESP_ERR_INVALID_ARG` / `ESP_ERR_TIMEOUT` / `ESP_ERR_NOT_SUPPORTED` |
| 失败条件 | 缓冲没对齐、`width*height*每像素字节` 与输入长度不符、输出缓冲不够（会报 DMA 描述符空）、单帧超时 |
| 易错点 | ①`src_type` 必须和相机输出格式一致（RGB565 ↔ RGB565）；②`sub_sample` 对 YUV422 输入只能是 4:2:2；③头里字段注释 `height/width` 写反了，按名字用：`width` = 水平像素 |

### `httpd_resp_send()` / `httpd_resp_send_chunk()`

| 项 | 内容 |
|---|---|
| 用途 | 前者发完整一段（带 `Content-Length`）；后者发 HTTP chunked 里的一块（MJPEG 每帧用） |
| 参数 | `httpd_req_t*`、数据指针、长度（`HTTPD_RESP_USE_STRLEN` = 用 `strlen`） |
| 返回 | `ESP_OK` / 发送失败（`ESP_FAIL` 或 socket 错误） |
| 失败条件 | 客户端提前断开、`send_wait_timeout`（默认 5s）内发不出去 |
| 易错点 | ①`/stream` 必须每帧先发 `Content-Length` 再发裸 JPEG；②收尾发 `httpd_resp_send_chunk(req, NULL, 0)`；③发送失败后**仍要把槽位还回队列**，否则 3 帧后彻底卡死 |

### V4L2（ioctl）

常用序列：`VIDIOC_S_FMT`（设 1024×600 RGB565）→ `VIDIOC_REQBUFS`（申请 2 个 mmap 缓冲）→ `VIDIOC_QUERYBUF` + `mmap` → `VIDIOC_QBUF` × N → `VIDIOC_STREAMON` → 循环 `VIDIOC_DQBUF` / `VIDIOC_QBUF`。

易错点：`VIDIOC_G_FMT` 拿到的默认格式不一定是你要的，`S_FMT` 之后要回读 `bytesperline`——不等于 `width * 2` 说明每行有填充，按紧凑排布喂编码器会错位。

## 5. 踩坑清单

1. **`main/CMakeLists.txt` 写 `PRIV_REQUIRES` 会覆盖默认依赖**：main 组件本来隐式依赖全部组件，一旦显式写了 Requires，`nvs_flash.h` 之类就找不到了。要么不写、要么把依赖列全。
2. **JPEG 输出缓冲必须 cache line 对齐**，否则 `jpeg_encoder_process` 直接失败。
3. **`reason=201`** = `WIFI_REASON_NO_AP_FOUND`：SSID 不在范围（手机热点没开）。不是密码错（那是 15 / 204）。
4. **PC 和板子不在同一网段时 curl 会拿到 302**：校园网/运营商认证页会抢答，看起来"服务器有响应"，其实是别人在回。
5. 相机 `S_FMT` 失败报 `input width=1024, height=600 is not supported` → 去 `sdkconfig.defaults` 把 SC2336 的默认格式改成 `1024X600`（见 P5 摄像头那节）。

## 6. 打不开时按层查

```
手机连的是板子所在的那个热点吗？        → 手机上看 Wi-Fi 名称
板子有 IP 吗？                          → 串口日志 "拿到 IP: ..."
80 端口通吗？                           → 手机浏览器开根路径 /
根页面能开、图不显示？                  → 看 /jpg 是否 503（等帧超时 → 相机没出图）
能出图但很慢？                          → 看 /jpg 日志的"发送 xx ms"；网络问题
```

## 7. 面试能讲的三句话

1. 相机采集、JPEG 编码、HTTP 发送分属三个执行体，用"槽位 + 队列"传递**所有权**，慢客户端只会丢帧、不会反压到相机。
2. 编码走 P4 硬件 JPEG（8 ms/帧 @1024×600），所以 30fps 采集期间 CPU 占用很低，瓶颈在 Wi-Fi 带宽（11~14 fps）。
3. 单帧 `/jpg` 与连续流 `/stream` 共用同一条取帧/编码路径，区别只在 HTTP 层是 `resp_send` 还是 `chunk`。
